# Phase 1N-K: ICMPv6 Neighbor Discovery Stage 1

Date: 2026-11-06 (America/Chicago)
Status: M5 focused/full Python tests and real dual-interface PCAP replay accepted; ready for review.
Baseline: Phase 1N-J PR #42 squash-merged to main at ba3ae7a; 647 M5 tests previously passed.

## Scope

Decode passive RFC 4861 **Neighbor Solicitation** (type 135) and
**Neighbor Advertisement** (type 136) messages into immutable typed
evidence, preserving the original Ethernet II, IPv6 and capture
provenance. This is vertical protocol Stage 1; it does not introduce
an NDP neighbor cache, host identities, state changes or new 2D graph
links. Stage 2 can build interface-scoped neighbor observation state;
Stage 3 can cross-reference DNS-SD AAAA against independently
observed IPv6 neighbor address claims.

## Standards and validity

- RFC 4861: https://www.rfc-editor.org/rfc/rfc4861
- RFC 4443 ICMPv6 checksum: https://www.rfc-editor.org/rfc/rfc4443

The decoder enforces hop limit 255, code 0, at least 24 bytes,
nonmulticast target IPv6 address, a correct ICMPv6 checksum over
IPv6 source/destination plus pseudoheader, and valid ND option
lengths in eight-byte units. Unknown options and reserved bits
are retained as opaque evidence.

A source-unspecified (::) NS is classified as a **Duplicate Address
Detection** probe only when sent to the target's corresponding
solicited-node multicast address and without a Source Link-Layer
Address option. The target may be tentative: no IPv6-to-MAC sender
binding is created. A solicited NA must not have a multicast
destination. Router, Solicited and Override flags are retained
independently, as is a correctly sized target link-layer address option.

On Ethernet, a one-unit source/target link-layer option has a
2-byte option header and six address bytes. Unknown or other-sized
options are never interpreted as an Ethernet MAC. The Ethernet
frame sender is also kept separate from any ND option claim.

IPv6 direct fixed-header Next Header=58 is supported. Extension
header chains, fragments and non-NS/NA ICMPv6 messages are
deliberately skipped rather than misinterpreted. No probes or
wire transmissions are generated by NOVXIS.

## Files

- novxis/protocols/icmpv6_nd.py: Scapy-independent NS/NA parser,
  checksum validator, DAD classification and immutable options.
- novxis/pipeline/ndp.py: Ethernet → IPv6 → ICMPv6 observation.
- novxis/cli/ndp_replay.py: local PCAP replay of typed NS/NA
  observations, with summary-only privacy mode.
- tests/protocols/test_icmpv6_nd.py: malformed wire and checksum cases.
- tests/pipeline/test_ndp_pipeline.py: complete frame pipeline.
- tests/cli/test_ndp_replay.py: synthetic on-disk PCAP replay.

~~~bash
git fetch origin

python -m pytest tests/protocols/test_icmpv6_nd.py \
  tests/pipeline/test_ndp_pipeline.py tests/cli/test_ndp_replay.py -q

~~~

Optional local replay of an existing authorized PCAP or PCAPNG:

~~~bash
python -m novxis.cli.ndp_replay /path/to/local.pcap --summary-only
~~~

The replay command does not require root. Without --summary-only it
prints original IPv6 and link-layer values to the local terminal.
Do not commit or share raw private PCAPs, MACs or IPv6 addresses.
An empty local capture is not a parser failure; synthetic fixtures
exercise supported messages deterministically.

## M5 acceptance: automated regressions and passive captures

The developer reported full results from their M5 MacBook Air,
Python 3.14.6 / pytest 9.1.1:

- Focused NDP tests: **64 passed in 0.08s**.
- Full regression suite: **711 passed in 3.96s**.
- Stage 1 added 64 passing tests beyond the previous baseline of 647.

They also replayed two locally held, authorized PCAPNG files via the
new Stage 1 command using `--summary-only`, with no decode errors:

| Capture interface | Frames | NS | NA | DAD | Decode errors |
| --- | ---: | ---: | ---: | ---: | ---: |
| en0 (Wi-Fi) | 508 | 32 | 32 | 0 | 0 |
| en5 (Ethernet) | 3,918 | 2 | 2 | 0 | 0 |

A private aggregate-only review of the uploaded PCAPNGs found
approximately 181 seconds of en0 traffic versus 36 seconds on en5,
with 8 distinct NS/NA target addresses on en0 and 2 on en5.
These durations are not controlled or equivalent capture windows;
packet totals alone must not be treated as interface traffic
performance comparisons.

Crucial future Stage 2 boundary: all 34 observed Neighbor
Solicitations included exactly one-unit **Source Link-Layer Address**
options, but **Target Link-Layer Address** options appeared in only
one of the 32 en0 Neighbor Advertisements and none of the two en5
Neighbor Advertisements. An NA without an explicit TLLA option
must not be treated as a verified target-to-MAC association.
The NS SLLA refers to the **soliciting source IPv6 address**, not
the NS target. Observations remain separate from device identity.

At least one Router Advertisement was also present on each interface
in these captures. Type 134 is correctly outside the Stage 1
NS/NA decoder scope and is deferred to a later milestone.
